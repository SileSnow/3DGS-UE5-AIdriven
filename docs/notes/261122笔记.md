## 3. 关键

1. 数据找不到。ZEUS 仓库里 `.glb/.ply/.obj/.tif/.las` = 0 个；`_data/README.md` 原文“输入数据（不进 Git）”；生成器在，但 FABDEM/GEBCO/GSI/parquet 输入都不在本地。→ 不能按“数据马上就有”排期。
2. 数据是白模，无纹理。

3. ZEUS 没有相机内参/位姿、没有斜视影像、没有深度/点云。训练视角只能来自 UE5 虚拟相机、无人机实拍或公开数据集。
4. 180,000 高斯是“街区级预算”，不是“高保真承诺”。 300 m×300 m = 9 万 m²，180k ≈ 2 点/m²；按东京密度约 227 栋，约 793 点/栋。要单栋细节应缩到 30–50 m 或提到 300k–600k。
5. 坐标必须读 `terrain.json.origin.kx/ky`，不能用常量。 ZEUS `KY = 110574`，本仓库 `mission_io.py` 用 `111320`，差 0.67%，5 km 处错 33 m。ZEUS 局部轴是 `x 东 / y 上 / z 南`，UE 是 `+X 东 / +Y 南 / +Z 上`。
6. L5 的两个 flag 是状态机，不是文案。 没训练就不能写 `trained_radiance_field: true`；没观测就不能把 `inferred_facades` 翻 `false`（要给 `observed_facade_ratio`）。
7. 邮件点名的四槽位/契约文件在 3 个分支（`main` / `research/building-hazard-simulation` / `archive/...`）+ GitHub tree 复核都查不到（0 命中）。 最可能是作者本地未提交；先按提案 v0.1 推进，回信确认。
8. 本仓库已有的 3DGS 基线是“合成校园场景”：v9 549,617 splat、1280×960、7k iter、val PSNR 18.74 / SSIM 0.70。它证明管线通，不代表东京画质。
9. UE5 mission 渲染器与“园区场景”硬绑定：`render_mission.py:50,114-125` 要求 mission 的 origin/camera 与固定园区（39.9042/116.4074/43、fx=1148.3429）一致，否则直接抛错。所以“换 mission 的 origin 就能换场景”不成立；接东京场景必须改场景构建与参数（见 §6.5）。

## 5. L4 → L5 接口草案（v0.1，待与作者原件对齐）

### 5.1 层次定义（提案）

| 层 | 范围 | 载体 | ZEUS 现有对应 |
|---|---|---|---|
| L0 | 全球城市 | 城市点/边界/全球指标 | `globe.js` / `site/data/global/profile.json` |
| L1 | 国家/区域 | 灾害源、行政区、气候 | `eq_sources` / `tc_tracks` / `admin_bounds` |
| L2 | 城市 | 0.04° 地形 + 正射 | `terrain.bin.gz` / `ortho/*.jpg` |
| L3 | 街区（0.02°） | 建筑分块 | `bld/t_*.bin.gz` |
| L4 | 单栋 | 轮廓 + 底高 + 层高 + 属性 | `buildings.parquet` / `bld/*.bin.gz` |
| L5 | 局部视口 ≤300 m | 180,000 高斯 + 场景元数据 | **当前不存在**（本草案） |

> L0–L5 是**空间尺度层**，不要和灾种“1–5 级强度”混用。

### 5.2 `l5_scene.json` 关键字段

```json
{
  "schema": "zeus.l5_scene/v0.1",
  "level": "L5",
  "viewport": "map3dview",
  "frame": {"origin_wgs84": {"lon": 139.7525, "lat": 35.665}, "axes": {"x": "east", "y": "up", "z": "south"}, "units": "m"},
  "extent": {"center": [0, 0], "size_m": [300, 300]},
  "gaussians": {"count": 180000, "file": "gaussians.ply", "format": "3dgs_ply_v1", "sha256": "..."},
  "l4_source": {"file": "l4_block.json", "building_count": 227, "tile_ids": ["t_5_8"]},
  "provenance": {"inferred_facades": true, "trained_radiance_field": false, "observed_facade_ratio": 0.0, "training_views": 0}
}
```

### 5.3 两个 flag 的状态机

| 状态 | inferred_facades | trained_radiance_field | 条件 |
|---|---|---|---|
| S0 proxy_only | true | false | 只从 L4 采样，未训练（本小样就在这一档） |
| S1 initialized | true | false | 已生成 180k，仍未训练 |
| S2 partially_observed | true | true | 用 ≥20 视角优化过，但 `observed_facade_ratio < 0.9` |
| S4 verified | false | true | `observed_facade_ratio ≥ 0.9` 且留出 PSNR 相对初始化基线 +≥1.5 dB |

> 部分观测时保持 `inferred_facades: true`，不要为了好看提前翻 false。
> 注意：S0 与 S1 的两个 flag 数值完全相同（true/false），单看 JSON 无法区分“未采样”与“已采样未训练”；需要另记 `stage` 或按 `gaussians.count` 判断。

### 5.4 与 PLY 契约对齐

- 每个高斯 62 float：`xyz / nrm3 / f_dc3 / f_rest45 / opacity / logscale3 / quat4`（`shared/CONVENTIONS.md` §2）。
- 单位：默认 `--unit m` 输出 ZEUS 局部米；`--unit cm` 才 `×100` 并转 UE 厘米。轴向 `ue_x=x, ue_y=z, ue_z=y`。接 pipeline 时显式选单位。
- 颜色 `f_dc=(rgb-0.5)/0.28209479`；不透明度 `logit(0.85)=1.735`；尺度取 `log(sigma)`（cm 导出时 sigma 以 cm 计）。

### 6.5 东京坐标复跑

2026-11-22 15:23 尝试用东京 origin（139.7525/35.665/43）+ 4×4×20 m 航线跑一次，**未出帧**，两个原因：

1. **温度守门**：`run_mission.ps1:143` 本地笔记本电脑温控，程序拒绝启动 UE，3.1 s 退出，未进场景，个人电脑跑不动；
2. **场景 origin 硬绑定**：`render_mission.py:50,114-125` 要求 mission origin 与园区一致（1e-7 容差），东京 origin 必然抛 `RuntimeError`。即使降温或 `-Force` 也过不去。

离线干跑是成功的：16 帧、0–67.824 s、GPS 往返误差 0.000 m、航点包围盒 60 m×60 m（20 m 间距）。
完整命令、报错原文与数字见 [`evidence/ue5_tokyo_attempt_2026-11-22.md`](evidence/ue5_tokyo_attempt_2026-11-22.md)。

**结论：本轮没有“东京场景接入”，也没有东京渲染帧。** 下一步二选一：A. 用园区 origin 重算同航线，先交“预定路线飞行”证据；B. 参数化/替换场景，再接东京（需拍板，属改源码行为）。

7. 以为改 mission origin 就能换场景：`render_mission.py:114-125` 固定园区 origin/内参，容差 1e-7；要参数化场景或换场景构建，不是改 mission
